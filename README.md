# Рядом — приложение такси для пассажиров и водителей (MVP)

Два интерфейса в одном приложении — пассажир и водитель (роль выбирается при первом запуске).

Пассажирский цикл: регистрация или вход по телефону и паролю → адреса → серверный расчёт стоимости → поиск водителя →
отслеживание автомобиля → поездка → оплата (ЮKassa) → история поездок.

> Среда проекта — Next.js (App Router) + PostgreSQL (Drizzle ORM). Flutter/Firebase в этом окружении
> недоступны, поэтому реализация выполнена как mobile-first веб-приложение с теми же архитектурными
> правилами: стоимость и статусы меняет только сервер, платежи — только через серверный API ЮKassa.

## Архитектура

```
src/
  core/            errors, phone, geo, widgets   — ядро без зависимостей от данных
  shared/          types, api (клиентский слой), session (сессия + уведомления)
  server/          auth, driver, geocoding, routing, pricing, fare-calculator, dispatch, orders, yookassa, seed
  features/        map, addresses, home, ride_order, driver_tracking, payment, authentication, driver — UI-модули
  app/             страницы пассажира (home, orders/[id], history, settings), водителя (driver, driver/history,
                   driver/settings), выбор роли (/) и API-роуты
  db/              schema.ts (Drizzle)
tests/             модульные тесты (node:test)
```

Интерфейс не обращается к БД — только через `src/shared/api.ts` → `app/api/*` → `src/server/*`.

## Ключевые правила

- Суммы — в копейках. Ставки тарифов хранятся только в БД, клиент их не получает.
- Оценка стоимости (`POST /api/fare/estimate`) сохраняется на сервере; заказ создаётся только по `estimateId`.
  В заказ записывается применённая версия тарифа (`tariffVersion`).
- Статусы заказа меняет только сервер (`src/server/dispatch.ts`, `src/server/yookassa.ts`).
- Платёж создаёт сервер (`POST /api/payments` → API ЮKassa). Webhook (`POST /api/payments/webhook`)
  не доверяет телу уведомления — статус перепроверяется запросом к API ЮKassa.
  Возврат из платёжного окна не считается подтверждением оплаты.
- Пассажир видит только собственные заказы (проверка владения в каждом запросе). Роль `passenger`
  не изменяется из приложения.

## Роли: пассажир и водитель

- **Первый запуск** (`src/app/page.tsx`): экран «Кто вы?» — пассажир или водитель. Выбор запоминается на
  устройстве (`src/shared/role.ts`). Дальше приложение открывается так:
  есть действующая сессия → сразу раздел роли учётной записи (`/home` или `/driver`), без входа и выбора;
  нет сессии, но роль выбрана → вход этой роли; ничего не выбрано → выбор роли.
  Сессия живёт 30 дней, поэтому регистрироваться каждый раз не нужно.
- **Смена роли:** кнопка «Сменить роль» на экране входа и в настройках. Одному номеру телефона соответствует
  одна роль: вход в чужой роли отклоняется (`role_mismatch`, проверяется только после верного пароля),
  регистрация занятого номера в другой роли — `phone_registered`.
- **Роль назначает только сервер.** Регистрация водителя создаёт в одной транзакции учётную запись
  (`users.role = driver`), профиль (`drivers.user_id`) и автомобиль. Поле роли из запроса принимается
  только как «driver»; любое другое значение — пассажир. Разделы закрыты друг для друга на сервере
  (`requirePassenger` / `requireDriver`, ответ 403).
- **Регистрация водителя:** имя, телефон, пароль и автомобиль (марка, модель, цвет, госномер, класс).
  Госномер нормализуется (латиница → кириллица, регистр) и проверяется по формату А123ВС70.
- **Интерфейс водителя** (`src/app/(driver)/driver`): карта и сворачиваемая панель.
  1. «Выйти на линию» (нужна геопозиция), «Уйти с линии» (нельзя во время заказа).
  2. Пока водитель на линии, его позиция уходит на сервер каждые 4 с (на стоянке — каждые 20 с);
     пассажир видит её на карте в реальном времени.
  3. Заказы рядом: только свой класс автомобиля, не дальше 30 км, срок поиска не вышел.
  4. «Принять заказ» — атомарно, заказ достаётся одному водителю.
  5. Поездка по шагам: «Выехал к пассажиру» → «Я на месте» → «Начать поездку» → «Завершить поездку»;
     до начала поездки можно отказаться (заказ вернётся в поиск, пассажир получит уведомление).
  6. Телефон пассажира и кнопка «Открыть в навигаторе» (Яндекс Навигатор, 2ГИС или Google Карты по профилю).
  7. «Поездки» — история, «Профиль» — имя, автомобиль, навигатор.
- **Статусы меняет только сервер** (`src/server/driver.ts`): он проверяет, что заказ принадлежит этому
  водителю и переход допустим из текущего статуса. При завершении сервер фиксирует итоговую стоимость и
  переводит заказ в `payment_pending`. Правила переходов — `src/core/driver-flow.ts`.
- **Демо-диспетчер и реальные водители:** пока есть свободный водитель на линии подходящего класса
  (позиция обновлялась не позднее 90 с назад), имитация не вмешивается — заказ ждёт реального водителя
  до 120 с, потом отменяется («Нет доступных водителей»). Если живых водителей нет, заказ, как раньше,
  обслуживает имитируемый водитель.
- Не реализованы: геозабор («Я на месте» не проверяет расстояние до точки подачи), заработок и выплаты
  водителю, документы и модерация водителей, изменение автомобиля после регистрации.

## Авторизация

- **Регистрация:** имя, номер телефона, пароль и повтор пароля. Пароль — от 8 до 128 символов.
  Сервер сохраняет только scrypt-хеш с индивидуальной случайной солью (`N=32768, r=8, p=3`).
- **Вход:** номер телефона и пароль. SMS-коды, их таблица, маршруты и переменная `SMSRU_API_KEY` больше
  не используются. Номер служит логином и не считается подтверждённым по SMS.
- После успешной регистрации или входа создаётся сессия на 30 дней; в БД хранится только хеш её токена.
  Пароль не сохраняется в localStorage, sessionStorage, window.name, cookie или диагностике.
- Защита от перебора: 10 попыток входа и 5 попыток регистрации на номер за 15 минут. Счётчики хранятся
  в PostgreSQL (`auth_attempts`), успешный вход сбрасывает счётчик. Ошибка входа не раскрывает наличие профиля.
- Повторная регистрация номера с паролем запрещена. Старый профиль без пароля может задать его через
  регистрацию: идентификатор, роль и история сохраняются, существующий пароль не перезаписывается.
- Восстановление пароля и смена пароля в настройках пока не реализованы.
- **Вход показывается на месте страницы** (`src/features/authentication/AuthGate.tsx`): экраны пассажира
  лежат в группе `src/app/(passenger)`, и без сессии вместо страницы рендерится форма входа — на том же
  адресе, без перенаправлений. После входа сразу отображается исходная страница. Если вход потребовался
  не на главном экране или сессия завершилась, показывается пояснение «Чтобы продолжить, войдите по
  номеру телефона и паролю. После входа вы вернётесь на прежнюю страницу.» `/login` оставлен как совместимый
  адрес и перенаправляет на `?next=` (с защитой от внешних адресов) или на `/home`.
- **Транспорт веб-клиента — `POST /api/rpc`, сессия в теле запроса.** Диагностика показала, что окно
  превью открывается через прокси, который пересылает только тело запроса и базовые заголовки:
  `Authorization`, `X-*`, `Cookie`, `Origin`, `Sec-Fetch-*` до сервера не доходят. Поэтому клиент
  (`src/shared/api.ts`) отправляет все вызовы на один адрес с конвертом
  `{ path, method, body, session }`. Сервер (`src/app/api/rpc/route.ts`) проверяет конверт, пропускает
  только API пассажира из явного списка (webhook ЮKassa и служебные маршруты недоступны) и вызывает
  те же обработчики, что и REST-маршруты, передавая токен через `AsyncLocalStorage`
  (`src/server/session-context.ts`). Бизнес-логика не дублируется. Content-Type не требуется.
- Сервер ищет токен по очереди (`src/server/session-transport.ts`):
  1. тело RPC-запроса — основной способ для веб-клиента;
  2. `Authorization: Bearer <token>` — для мобильного клиента и прямых REST-вызовов;
  3. `X-Session-Token` — дубль на случай, если прокси перезаписывает `Authorization`;
  4. httpOnly-cookie `taxi_session` — запасной способ при прямом доступе без прокси. По HTTPS она
     `SameSite=None; Secure; Partitioned` (CHIPS), по HTTP — `SameSite=Lax`. Cookie принимается только
     вместе с заголовком `X-Taxi-Client` — межсайтовая форма не может его добавить, поэтому CSRF
     невозможен. Токен в теле CSRF не подвержен: чужой сайт его не знает.
- Клиент хранит токен в памяти и в `localStorage`. Если хранилище заблокировано (встроенное окно при
  блокировке сторонних данных), токен держится в `window.name`: оно переживает перезагрузку окна и не
  зависит от cookie и заголовков. Перед переходом на страницу оплаты `window.name` очищается.
- Проверка: `tests/browser/login-through-proxy.cjs` поднимает прокси, удаляющий заголовки и cookie,
  и проходит регистрацию, вход, переход по разделам, перезагрузку, выход и повторный вход в Chromium (обычная вкладка, окно на чужом
  сайте, окно с заблокированным хранилищем).
- Ответы на запросы, начатые до нового входа, не могут сбросить новую сессию (счётчик входов).
- HTML-страницы отдаются с `Cache-Control: no-store` (`dynamic = "force-dynamic"`), чтобы прокси не
  отдавали устаревшую страницу после пересборки.

### Диагностика доставки сессии

Таблица `auth_diagnostics` (без токенов, хранение 3 дня) фиксирует, какие способы передачи сессии
дошли до сервера и имена дошедших заголовков (`header_names`): события `register_ok`, `login_ok`, `login_failed`,
`me_ok_body|authorization|header|cookie`, `me_unrecognized`, `me_anonymous`, `unauthorized`. Пример запроса:

```bash
psql "$DATABASE_URL" -c "select created_at, event, body_session, via_rpc, authorization_header, cookie, header_names from auth_diagnostics order by created_at desc limit 30"
```

`GET /api/diagnostics/transport` возвращает те же признаки для текущего запроса. Значения паролей
и токенов не записываются. После входа клиент проверяет сессию контрольным запросом `/api/auth/me`.

## Оплата во встроенном окне

Страница ЮKassa не открывается внутри фрейма, поэтому во фрейме она открывается в новой вкладке;
в обычной вкладке — переходом. `return_url` строится от публичного адреса (`APP_BASE_URL`, затем заголовок `Origin`
браузера — прокси превью передаёт `x-forwarded-proto: http` даже при HTTPS — затем `X-Forwarded-*`) и ведёт на `/payment-return`, который оплату не подтверждает. Статус незавершённого
платежа сервер сверяет с API ЮKassa при каждом опросе заказа (не чаще раза в 5 с) и по webhook.

## Зоны обслуживания

- В интерфейсе заказа нет выбора тарифа: используется первый доступный в зоне подачи тариф
  (по `sort_order`, по умолчанию «Эконом»). Цена и время подачи показываются для него.
- Доступность тарифов определяется по точке подачи: таблица `service_zones` (город, центр, радиус)
  и `tariff_zones` (какие тарифы есть в городе). Логика выбора зоны — `src/server/service-area.ts`.
- По умолчанию заполнены 35 крупных городов России. «Эконом» и «Комфорт» есть везде, «Бизнес» — в
  городах-миллионниках и Томске. Заполнение выполняется, только если таблица пуста, поэтому ручные
  настройки не перезаписываются.
- **Пригород и область:** точка вне городской зоны, но не дальше 250 км от её границы
  (`SUBURBAN_RANGE_KM` в `src/server/service-area.ts`), обслуживается ближайшим городом. Доступны его
  тарифы без премиальных классов («Бизнес» только в городе), а время подачи увеличивается на дорогу
  из города (~60 км/ч). Название зоны в интерфейсе заказа не отображается.
- Дальше пригородной зоны сервер отвечает `out_of_service_area` и называет ближайший город
  обслуживания и расстояние до границы его зоны. Поездки длиннее 150 км по прямой отклоняются с кодом `trip_too_long`.
- Добавить город:

```sql
insert into service_zones (id, name, latitude, longitude, radius_km) values ('tula', 'Тула', 54.1931, 37.6173, 30);
insert into tariff_zones (tariff_id, zone_id) values ('econom', 'tula'), ('comfort', 'tula');
```

## Демо-диспетчер

Приложение водителя не подключено, поэтому `src/server/dispatch.ts` имитирует назначение водителя
и его движение (помечено в интерфейсе). При подключении реального диспетчера модуль заменяется без
изменений клиента.

## База данных: Yandex YDB

Серверная часть работает через `@ydbjs/drizzle-adapter`, а не через PostgreSQL.

| Переменная | Назначение |
|---|---|
| `YDB_CONNECTION_STRING` | строка подключения serverless YDB, например `grpcs://ydb.serverless.yandexcloud.net:2135/ru-central1/...` |
| `YANDEX_SA_KEY_JSON` | JSON авторизованного ключа сервисного аккаунта |

Ограничения YDB учтены в коде:

- идентификаторы создаёт приложение (`crypto.randomUUID()`), база их не генерирует;
- внешних ключей и каскадов нет: связанные строки удаляет `deleteUserData`;
- захват заказа — условный `UPDATE ... RETURNING`, а не блокировка строки;
- счётчик попыток входа — отдельный `SELECT`, затем `INSERT` или `UPDATE`;
- `uuid` хранится как `Utf8`, JSON — как `Json`, время — как `Timestamp`.

Без этих переменных интерфейс открывается, а запросы к данным сообщают, что база не настроена.
| `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` | ЮKassa. Без них оплата недоступна (явно сообщается) |
| `APP_BASE_URL` | публичный URL для `return_url` платежа |
| `OSRM_BASE_URL` | свой OSRM (по умолчанию — публичный демо-сервер) |

## Не реализовано (явно)

- Push-уведомления (FCM/Web Push) — заменены in-app уведомлениями через опрос `/api/orders/events`.
- Сохранённые способы оплаты (токенизация ЮKassa).
- Yandex Pay.
- Восстановление и смена пароля.
